## 性能测量

环境：Linux x86_64、72 个逻辑 CPU，Intel Xeon E5-2686 v4 @ 2.30GHz，内存 251GiB；本地 ext4 `/dev/nvme0n1p2`，无 NFS。Rust/Cargo 1.98.0、Node 24.20.0、pnpm 11.24.0、SQLite 3.51.3。此主机同时承载其他会话，不是隔离的基准环境。

NFR-001 目标为 50 次提交/秒 × 60 秒，p95 < 250ms。脚本使用 release 二进制、全新数据库、同一受信版本、不同幂等键；包含每次实际 Git 校验，尚未拆出“已解析版本”的纯入账时间。配置：WAL/FULL、tick 250ms、coalesce 2000ms、模拟阶段 500ms、全局上限 2、单 lane 上限 1。

```bash
cargo build --release --locked
# 使用独立本地测试配置/数据库和环境变量令牌启动服务后：
python3 scripts/load.py --url http://127.0.0.1:8788 \
  --lane demo-test --revision <镜像内的完整受信 SHA> --rate 50 --seconds 60
```

第一次压测在 Git 校验持有写锁、持久层序列化全部历史时堆积，主动中止：[baseline.json](baseline.json)。将提交授权的 Git 校验移出写锁后仍堆积：[load-optimized.json](load-optimized.json)。它们均明确记录为未完成，不计为通过。

最终增量序列化版本（`14fe6af`）完整测量：[load-delta.json](load-delta.json)。3000 个请求全部返回 202，最终数据库中 3000 个请求均已 satisfied；但积压使总耗时达到 **162.323 秒**，响应 p50 **1452.377ms**、p95 **14265.768ms**。

**本次端到端负载未达目标，NFR-001 不通过/不关闭。** 该数值包含 Git 校验，已解析版本的纯入账延迟尚未独立测量；不能把它表述为已经达到纯调度性能指标。后续需要针对全量状态克隆、候选/覆盖计算与磁盘提交做分阶段采样，解决随历史积累增长的成本，再完整重测。目标没有被悄悄降低。
